# Architecture

## Overview

A single Cloudflare Worker serves both the API and the React single-page app.

```
Browser ──► Cloudflare edge
             ├─ /api/*, /q/*, /t/* → Worker (Hono) ──► D1 (all data, incl. logos)
             │                                     ├─► Rate Limiting binding
             │                                     ├─► Workers AI (optionally via AI Gateway)
             │                                     └─► WhatsApp, Razorpay, Twilio (optional Gemini)
             ├─ cron (every min / 09:00 IST) → outbox delivery, automations, subscription expiry
             └─ /*      → Static assets (React SPA, Workers Static Assets)
```

| Layer | Technology |
|---|---|
| API | Hono on Cloudflare Workers |
| Database | Cloudflare D1 + Drizzle ORM |
| Auth | Better Auth for staff; lightweight phone-based sessions for customers |
| Files | D1 BLOBs (logos ≤ 300 KB; R2 intentionally not used) |
| Background jobs | Cron Triggers + D1 outbox (`notification_logs`) — no Queues required |
| Frontend | React 19, React Router, TanStack Query, Tailwind CSS 4 |
| Build/dev | Vite 8 + `@cloudflare/vite-plugin` (dev runs in real `workerd`) |
| Tests | Vitest + `@cloudflare/vitest-plugin` (tests run inside `workerd`) |

## Source layout

```
src/
  shared/          Code used by both Worker and client (permissions, categories)
  worker/
    index.ts       Hono app: middleware order, route mounting, error handling
    auth.ts        Better Auth factory (per request, bound to env)
    db/            Drizzle schema + client
    middleware/    Session loading, tenant guard, rate limiting
    routes/        me, businesses, locations, staff/invitations, admin
    lib/           Errors, validation, audit, crypto, password hashing, mailer
  client/
    pages/         Route screens
    layouts/       Dashboard shell
    components/    UI kit
    lib/           API client, auth client, queries
migrations/        SQL migrations (generated by drizzle-kit, applied by wrangler)
test/              Integration tests
```

## Security model

- **Authentication**: Better Auth with HTTP-only session cookies stored in D1. Secure cookies in production.
- **Password hashing**: PBKDF2-SHA256 (100,000 iterations, the Workers maximum) via WebCrypto. Better Auth's default JS scrypt can exceed Workers CPU limits.
- **Platform roles**: `users.role` is `user` or `super_admin`. It cannot be set through sign-up (`input: false`) and is changed only via a database command.
- **Tenant isolation**: every business-scoped route lives under `/api/businesses/:businessId/...` and passes through `requireBusiness()`. That middleware loads the caller's active membership, rejects suspended businesses, checks the required permission and puts the business on the context. Handlers only use `c.var.membership.business.id`, never ids from the request body. Child records (locations, staff, invitations) are always queried with both their own id *and* `business_id`. Missing and foreign businesses return the identical 404, so ids can't be probed.
- **Staff permissions**: roles are `owner`, `manager` and `staff`, each with defaults. Owners can set a custom permission list per member. `business.manage`, `staff.manage` and `billing.manage` are owner-only and can never be delegated, which prevents privilege escalation.
- **Invitations**: random 256-bit tokens. Only the SHA-256 hash is stored. They expire after 7 days, are single-use and revocable, and can only be accepted by an account whose email matches the invitation.
- **Rate limiting**: Workers Rate Limiting binding. Auth is limited to 20/min per IP and the API to 300/min per IP.
- **CSRF**: Better Auth validates `Origin` against `trustedOrigins`. Cookies are `SameSite=Lax`, and API mutations take JSON, which forces a CORS preflight cross-origin.
- **Bot protection**: Cloudflare Turnstile on sign-up and sign-in when `TURNSTILE_SECRET_KEY` and `VITE_TURNSTILE_SITE_KEY` are set.
- **Uploads**: logo type allow-list (PNG/JPEG/WebP), magic-byte check, 1 MB limit, random object keys, served with `nosniff`.
- **Audit log**: every mutation writes an `audit_logs` row in the same D1 batch as the change.

## Atomicity on D1

D1 does not support interactive transactions. Multi-statement writes use `db.batch([...])`, which D1 executes atomically. Duplicate prevention relies on UNIQUE constraints. The future loyalty engine will use an idempotency key unique index on `stamp_transactions`.

## Modules

- **Loyalty Engine** (`services/loyalty-engine.ts`): `issuePoint()` and `redeemReward()` are the only code paths that change balances; QR, NFC tag and staff-assisted channels all call them. Each point is an append-only ledger row written in the same D1 batch as the balance update. The database itself enforces single use (UNIQUE idempotency key), the daily limit under concurrency (UNIQUE daily slot) and non-negative balances (CHECK).
- **Customer QR** (`services/card-token.ts`): the card shows an HMAC-signed token (key derived from the auth secret) valid for 90 s; staff scan it and the server verifies signature, expiry, business ownership and single use. Printed business QR codes and NFC tags only open the business page.
- **NFC tags**: tap → `/t/:code` → customer creates a 5-minute request with a 4-digit code → staff approve in the scanner → engine issues the point. For cryptographic per-tap anti-replay without staff, NTAG 424 DNA (SUN/SDM) tags would be the next step.
- **Phone-to-phone NFC**: not possible in browsers (Web NFC can't emulate a card; iOS has no Web NFC; HCE isn't open to apps in India). Needs a native Android HCE app; the web app detects capability and falls back to QR.
- **AI reviews** (`services/review-ai.ts`): Cloudflare Workers AI by default (`env.AI.run` with JSON mode, optional AI Gateway); Google Gemini selectable with `AI_PROVIDER=gemini`. Same prompt and validation for both: exactly three drafts, length caps, no URLs, and Hindi/Gujarati drafts must be in the right script. Usage and estimated cost logged per call. Offered to every visitor, never linked to loyalty, never auto-posted.
- **CRM** (`services/segments.ts`): SQL aggregates per customer per business; consent table per business/channel.
- **Marketing** (`services/marketing-cron.ts`, `services/whatsapp.ts`): campaigns enqueue rows into the `notification_logs` outbox (consent-checked, deduped, capped); a per-minute cron claims and sends them via the WhatsApp Cloud API with retries; the webhook updates statuses and handles STOP.
- **Billing** (`services/razorpay.ts`, `services/plans.ts`): Razorpay Orders + Checkout with signature verification and idempotent activation; plan limits are read from the database and enforced in every module.
